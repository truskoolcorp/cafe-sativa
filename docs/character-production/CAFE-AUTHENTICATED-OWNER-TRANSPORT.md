# Finite authenticated owner-preview transport (inert proposal)

Base bb825274. No route, UI action, flag, live grant or production row. Existing service-key createAdminClient cannot call the owner-only writer and is intentionally not used. Existing cookie-bound createClient plus auth.getUser supplies the current user session.

## Trust boundary and scope
A new postgres-owned fixed scalar helper derives auth.uid/auth.role from PostgREST-validated JWT context, requires original SET ROLE context authenticated, requires JWT role authenticated, requires matching JWT sub and exact corporate owner UUID 54b71f3f-19e1-46f0-99e2-28993463caf8, and checks current auth.users app_metadata through the existing strict admin helper. user_metadata is never authority. Delegated content admins are not automatically owners. A service-role JWT with owner sub is refused. SQL's request.jwt.claims is trusted only when set by the authenticating proxy; direct trusted database administrators can forge settings, as they can already alter the database.

Helper EXECUTE is only postgres and cafe_metricool_owner. The separate cafe-owned SECURITY DEFINER wrapper is executable by authenticated, but that ACL alone grants no approval: every request passes the fixed owner/admin/JWT checks. cafe_metricool_owner gains no auth schema or table access. Existing underlying writer stays owner-only, and all four dispatch grants stay unchanged. No new role memberships persist.

Wrapper accepts only exact plan, snapshot, digest, reservation keys, source CAS and finite expiry. There is no supplied actor, approval timestamp, policy record or owner message reference. It generates authentic fresh-owner-preview provenance from the authenticated owner and exact digest, then delegates the unchanged writer's digest checks, current source locking/CAS, QA, expiry bounds and insert-once behavior. It neither fabricates Sentinel IDs nor converts a standing policy assertion into consent.

The server module offers a dedicated recordConfirmedPreview operation, NOT the existing authorityRpc callback. It pins a server-reviewed plan/digest, checks the current exact owner again, recomputes snapshot digest, clones arguments before awaiting, bounds auth waiting with an abort race, latches the one RPC attempt, uses only the existing cookie client, and makes one bounded abort-aware RPC with no retry/service-key fallback. It rejects extra fields including actor and policy assertions. No generic worker may silently adapt the standing-policy composition into this interactive path.

## Later activation prerequisites
A separate same-origin POST action must display the exact immutable plan/digest preview, require an explicit owner submit, reject other methods/origins/nonempty or unexpected payloads as appropriate, then invoke this dedicated operation. GET/preview must never write. No such route or button is enabled here. The explicit confirmed-preview marker in this server-only module is an integration contract, not independent proof of a user click; a reviewed route must establish it rather than accept arbitrary request JSON. A genuinely valid unscheduled candidate and all real QA are still required. Unknown write outcomes require read-only reconciliation, not replay.

This enables a finite first-delivery owner approval path after review, not unattended standing authorization. A future worker recording capability requires its own genuinely constrained enrollment/policy authority design; no per-post clicking is proposed as the steady state.

## Installer and tests
The proposal pins current installed function definitions (including repaired replay suppression), exact owners and current four dispatch/owner-only writer ACLs. It pins the dedicated owner bootstrap topology. Existing function bodies/ACLs, schema permissions, memberships, policies/default ACLs, table/column privileges, triggers and source/private data are preserved. Temporary owner SET/public CREATE are removed. Two new functions and their exact grants are the only persistent change. This needs scoped review/authorization, not merely merge approval.

Disposable PG17 fixture runs after the store/writer, replay repair and four-grant fixtures. It models PostgREST role/claims with exact provider auth function definitions; it does not verify JWT cryptography. Positive exact owner request must create one finite approval with derived actor and fresh provenance; service/anon roles, service JWT, missing sub, other admin, mismatched legacy sub, revoked admin and duplicate attempts are rejected. Rollback/injected abort and no underlying writer/auth-schema grant are checked. Actual PG17 CI required; local Python compilation is not DB proof. Eight local server tests pass; project strict TS must run in CI.
