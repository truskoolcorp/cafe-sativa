# Durable text concierge compatibility and recovery

Local implementation only. Do not enable or deploy this flow until the reviewed migration, synthetic database validation, explicit policy configuration, writer coordination, privacy/deletion lifecycle, and rollout approvals are complete. No production retention, replay-age, capacity, or spending setting is selected by this code.

## Capability and immutable request contract

`CONCIERGE_DURABLE_MODE` defaults to `off`. `on` enables ledger admission; any other nonempty value fails closed. The browser reads the uncached `GET /api/concierge/status` capability before sending. It requires `text_admissions_enabled` and, when durable mode is enabled, `durable_payload_version: 2`. Unknown or older capabilities fail closed rather than silently downgrading. In off mode, the previous page-local guest-session fallback remains available if browser storage is blocked. In on mode, the exact original body and request UUID must be durably retained before transmission. Existing retained work is never silently discarded or converted into legacy work.

New durable requests contain a UUIDv7 `request_id` and an integer `issued_at` in Unix epoch milliseconds. The UUID's first 48 bits encode that same issuance time. The browser creates both once using its clock and cryptographically secure randomness, then persists the serialized body before transmission. Neither a retry, reload, status check, authentication callback nor a server handler replaces the ID or refreshes the timestamp. The v2 canonical database payload contains exactly `version`, `issued_at`, `host`, `message`, `conversation_id`, `surface`, and `room_id`. An explicit timestamp that does not match the UUID is invalid.

The timestamp embedded in the key matters: a mutable timestamp beside an ordinary UUID would allow a purged key to look new. Database admission validates the immutable key age using the database clock, configured `replay_max_age_seconds` and `max_future_skew_seconds`, and a persistent monotonic `reject_before` watermark. Cleanup advances that watermark before removing keys; later policy widening cannot revive a removed key. These controls have no approved production defaults. The API does not independently estimate missing-key eligibility from the browser clock or application-server clock.

Browser requests carry `X-Concierge-Durable: 1` for durable sends/recovery or `0` for legacy sends. The server rejects a mode mismatch before any paid work or ledger admission. This fences configuration changes between the capability read and POST. External legacy mall callers without this header remain compatible in off mode, including opaque non-UUID sessions. To create new durable work they must upgrade to a client-retained UUIDv7 and matching issuance time. The server no longer generates a request ID for a durable caller that omitted it.

## Recovery, age and older clients

Only an explicit database status result can authorize replay. `202 recovery_required: true` can describe an eligible missing v2 key or an existing recoverable reservation. The API forwards a missing-key grant only while durable mode is on, text maintenance is off, the body is v2, and the database explicitly grants it. A bare `request_missing` from older SQL does not authorize replay. The browser then POSTs only the identical stored body and UUID. The entire status/replay sequence remains a recovery attempt: a transient denial such as `admitted: false`, quota exhaustion or policy unavailability cannot release its retained ID, because it does not fence a delayed original send and creates no permanent rejection tombstone. Only a committed reply or an explicitly verified terminal outcome can end that recovery chain. A delayed original admission and that replay compete for the same atomic ledger key; only an unambiguous fresh admission may dispatch. Status itself never dispatches, and admission rechecks the age/policy/watermark even if time or cleanup changed after status.

Retained v1 bodies remain readable without rewriting their six-key canonical payload or hash. Existing keys can still return their original state or cached answer. Missing v1 keys cannot become new durable work. Missing expired v2 keys return `request_expired`, never a recovery grant. An expiry/redaction error code alone does not prove that the original message was never processed or is no longer in flight. Without an explicit database `terminal: true` marker, the browser retains the original record and asks for support. The database may positively mark a redacted completed/cancelled/failed row terminal. For a missing key, only immutable v1 rejection or UUIDv7 issuance at or below the committed monotonic rejection floor permits the terminal marker. Age-only expiration above that floor is reversible if the policy widens or the database clock moves backward, so it stays nonterminal and retained. Unresolved rows are never pruned; the API forwards only the explicit database marker. A verified terminal result releases the composer without automatically resending the original text. No path refreshes a retained identity. Recovering an existing committed response remains possible after the admission horizon while its record/cache exists. Redacted/expired cached content is not regenerated.

Missing, disabled, or unavailable status while mode is off never grants replay. Unknown dispatches remain charged and are never retried at the provider. A client clock too far ahead or behind cannot be fixed by changing a retained request's issuance time; resolve the original first, then correct the clock before making a genuinely new request.

## Text-only maintenance and controlled drain

`CONCIERGE_TEXT_MAINTENANCE=on` rejects every new main `/api/concierge` POST before authentication, database access, legacy quota checks, ledger admission or provider use, including direct, legacy, mall and durable callers. Unset or `off` preserves normal behavior; any other nonempty value rejects admissions as invalid configuration. The gate does not claim `admitted: false`: a received POST may be a retry of an already admitted ID.

`GET /api/concierge/status` reports `text_admissions_enabled: false`. The browser disables new text sends but keeps the original-message status control available. Status POSTs remain read-only and available even during maintenance, including recovery of cached completions; admission-replay grants are suppressed. Already admitted workers retain their completion/finish path. Separate event/watch/video/YouTube routes and the independent live-voice component are not modified by this text gate. This is not a claim that unrelated services are healthy.

**Deployment-local configuration is not a global kill switch.** Changing this variable or switching a public alias does not modify previously deployed workers, already admitted work, alternate deployment URLs, direct callers or old automation. An old accessible deployment can still call the legacy provider path. Before declaring a cutover safe, inventory every public alias/deployment and mall/automation entry point; verify each can no longer initiate legacy work, using separately authorized deployment/access controls where required. Do not create bypass URLs or disable event/watch/YouTube access to solve a text-only drain. Drain and reconcile known in-flight work using verified terminal evidence before recording the database-clock legacy cutoff or `legacy_drained` state. Test both legacy and durable direct calls against the actual reachable entry points after the reviewed rollout.

Do not merely set durable mode off while durable work is outstanding: that reopens the legacy quota path. Keep the compatible durable worker, status, completion and ledger available. Pause new admissions with the reviewed database policy as well as the tested text gate when appropriate; verify rollout coverage instead of assuming a process-local flag stopped every worker. Drain reservations and reconcile dispatched/uncertain work. Only switch to legacy mode if rollback is approved and accounting compatibility and all unresolved work have been verified. Preserve the replay/tombstone horizon. Time passing, an aborted browser request, or a provider timeout is not evidence that provider execution ended.

## Provider evidence and failed storage

After a successful provider response, the worker constructs a strict four-field receipt: nullable provider `request_id`, `message_id`, `input_tokens`, and `output_tokens`. IDs must be ASCII letters/digits/underscore/hyphen, at most 128 characters; token counts must be nonnegative integers no greater than 2,147,483,647. Invalid/missing fields become null. No prompt, reply, error body, credentials, user/session identity or owner token is placed in this receipt. It is supplied only to the private completion/finish transaction and never included in browser responses.

The receipt is supplemental evidence, not authority to retry a provider call, refund an unknown request, or assert that an unacknowledged database write committed. After a positively received terminal provider response, two failed completion attempts and a final status check without a committed answer lead to a charged `provider_terminal_failure` finish. A verified terminal finish acknowledgement can release the browser composer; a concurrently committed completion wins and returns only its committed cache. A lost finish acknowledgement remains pending for status recovery. Provider/network exceptions remain charged/held as uncertain and are never automatically replayed. There is no new public reconciliation endpoint or logging sink. Operator evidence access, provider-side reconciliation, receipt retention/redaction, cleanup scheduling and monitoring still require the reviewed operational rollout; a receipt alone does not establish that those processes are configured.

## Identity, storage and validation

Durable browser requests carry `X-Concierge-Requester` with the retained request's expected `user:` or `guest:` identity. Before quota, memory, admission or status RPC, the server compares that expectation with verified authentication and the normalized original session. The hint cannot confer authority. Missing or mismatched hints on fenced browser requests return `409 requester_changed`, retaining the original request for its original identity. This closes the window where another tab changes login before this tab receives the auth callback.

Pending browser work uses per-request keys rather than one overwritable slot per account/host. Concurrent tabs may discover more than one unresolved request; each retains its original body and can be recovered separately. While definitively signed out, the browser may recover retained guest requests for the current host from the same browser, including a guest session created by a racing first-use tab. Recovery uses that record's original session and requester fence, never a signed-in user's identity. New sends remain blocked until unresolved work is handled. Malformed retained records fail closed.

Validation consists of mocked route/client I/O, local type checks, and the separately documented isolated database suite. It does not establish production database concurrency, alias coverage, actual provider quota, cleanup scheduling or rollout safety. No live provider request, deployment, migration, policy activation or permission change is performed by these tests.
