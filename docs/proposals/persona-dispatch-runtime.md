# Dormant one-shot persona dispatcher

This separate local increment starts from the frozen review-runtime candidate. It adds a one-shot server-only execution path, not a cron, recurring publisher, new destination, new asset generator or approval grant. Both `CS_PERSONA_REVIEW_RUNTIME_ENABLED=true` and **separately** `CS_PERSONA_DISPATCH_ENABLED=true` are required. Defaults perform no client construction, credential access, source read, signing or provider activity. No actual production action was taken while implementing or testing this proposal.

## Explicit request and transmission

The review workspace displays a separate scheduling confirmation only for exact current content with all dispatch prerequisites and no target attempt. It identifies the approved private MP4 hash/bytes, caption, future time and named account. Its unchecked consent explicitly authorizes transmitting those exact private bytes to Metricool for that social destination and scheduling the post. Content approvals and code rollout alone are not this transmission decision.

POST `/api/admin/programming/character-promos/dispatch` accepts only planId, reviewedDigest, explicitConfirmation:true and transmitApprovedVideo:true. Same-origin bounded JSON and fresh authenticated administrator identity are required. The service-side owner allowlist and captured authority epoch independently restrict who can dispatch. No actor, account, URL, storage path or arbitrary provider argument comes from the request. All request/response diagnostics are sanitized. A successful receipt says **scheduled**, never published.

## Transaction and uncertainty boundaries

1. Fresh auth user and current active owner epoch are captured once. The epoch is never replaced within the request, including after revoke/restore.
2. Current approved source bytes, exact eight QA observations, real script, canonical payload revision/rights assertions, all explicit content gates and final delivery approval must match the displayed digest.
3. The new service-only owner-bound claim wrapper locks the same parent draft, verifies caller epoch after waiting, and delegates existing atomic one-shot claim semantics. It binds dispatch_actor/dispatch_epoch to the **existing** permanent attempt row; no second attempt ledger or reset is added.
4. The original content approver epoch and dispatcher caller epoch must both remain valid. A postclaim token must match this plan/caller/epoch and still be submitting. Completed, unknown, expired or legacy unbound claims cannot be adopted or retried.
5. Only an acknowledged durable token permits submit setup. If the claim commits but its response is lost or malformed, there is no signing/create call and the attempt remains a manual hold. No network/HTTP retry is attempted.
6. Sources are reread after claim. The provider adapter rechecks approved stored bytes before opening its session. Lightweight fresh-auth/owner+approval and pinned-connection preflights run before signing and immediately before create; they do not redownload media or open new sessions.
7. A short-lived, exact content-addressed private-object URL is the existing narrow provider handoff. No public bucket, public permanent URL, file permission change or unapproved derivative is created. Provider readback must match returned id+UUID, exact caption/time/one network and actual hosted bytes.
8. Any ambiguous write, postclaim failure, lost receipt or finish error remains consumed/unknown or durable-submitting for reconciliation. The UI locks after an attempt, but SQL remains the cross-tab/restart authority. No automatic retry, reapproval or fallback destination exists.

## Fresh connection and time budgets

The session factory uses the existing encrypted authorized connection with no OAuth refresh/save. It pins actual provider/owner/status/brand/user/ciphertext/error/updated_at fields, rechecks current owner administration and token expiry, exposes only three fixed provider methods, and consumes create permission before invocation. Each failure latches that session closed. No raw credentials or private provider URL are returned to the browser.

`updated_at` exists but has no automatic revision trigger. A revoke/restore that restores every pinned field without advancing updated_at is not observable through this connection record; this limitation is not represented as sticky connection revocation. Caller/content-owner revocations do have their separately installed epoch protection.

The existing provider MCP session has a 25-second absolute budget. Private download/full-source revalidation occurs before opening it. CDN byte readback has a separate bounded 15-second fetch, and the route as a whole can take longer than 25 seconds. Deployment must provide sufficient route budget and validate provider behavior/timing before activation. Timeouts after a claim are permanent reconciliation cases, not retry permission.

No local DB lock can atomically govern an external provider request. Authorization or remote canon may change after the final preflight and before/during provider processing. The preflight minimizes this interval but does not claim cancellation or transactional protection across it. Once create is attempted, uncertainty is held permanently; later revocation cannot establish that a scheduled post was cancelled.

## Separate production gates

- Obtain approval for code publication/deployment separately from SQL/security rollout and from content/transmission consent. A denied remote commit must not be retried without the specific new authorization.
- Apply and verify all prerequisite review-runtime SQL, strict grants, sticky owner epochs and auth triggers. No migration is automatic.
- Separately approve the dispatcher proposal's two nullable metadata columns on existing attempts and service RPC grant change: revoke direct legacy claim execution for service_role and grant only the owner-bound wrapper/preflight. Existing unbound rows stay nonretryable holds, with no fabricated actor backfill.
- Verify actual schema parity, original approver+caller revocation behavior, feature flags, server route budgets, exact destination mapping and provider create/readback contracts. Hosted concurrency tests must actually pass; local single-user fixtures are not race certification.
- Obtain real current-video QA, desired future captions/times and explicit owner voice/video/publication/final delivery approvals for each wanted plan. Review/withdraw unwanted sibling plans explicitly. Engineering rollout does not fill missing evidence.
- Only then deliberately activate the separate dispatcher flag and obtain an explicit user transmission/scheduling decision. No real provider operation has been exercised by these tests, so production provider behavior is not proven here.

## Remaining scope

The code path is now connected locally, but activation remains blocked by the above engineering/security and user-consent gates. There is no recurring schedule creation, automatic reapproval, new-plan/account authoring, provider cancellation, automatic recovery of unknown claims or assertion of publication. Reconciliation of an attempted target remains manual. Existing already-approved unattempted sibling plans can dispatch after a sibling claim; their own current exact approval and future slot remain mandatory.

## Provider contract evidence, not live certification

Parent-performed authorized read-only connector calls during this task verified Tru Skool brand5373515/user4174093, timezone America/Chicago, Facebook146219355471397 and Threads truskoolcorp. Actual getScheduledPosts data confirmed the existing post shape described below, including provider PENDING metadata and a static.metricool.com MP4 URL. Available official tool input schemas match the adapter names and argument fields. No existing reminder was changed, copied or scheduled by this work. Source inspection verifies the existing client initializes MCP, lists tools and resolves the names below. Runtime now requires exactly one matching tool identity for each name; it does **not** pretend that name existence validates the provider's input/output schema.

- `getBrandSettings({})`: adapter expects an array or `.data` array with id, userId, networksData.facebookData/threadsData and timezone.
- `getScheduledPosts({brandId,fromDate,toDate,timezone,extendedRange:false})`: expects an array or `.data` array; matching rows require id, uuid, text, publicationDate.dateTime/timezone, exactly one providers.network, autoPublish:true, draft:false and a single media URL.
- `createScheduledPost({blogId,date,mediaFiles:[exactSignedURL],info:JSON.stringify(...)})`: info contains exact caption, one named provider, publication date/timezone, autoPublish:true, draft:false and the existing network-specific POST fields. Adapter expects trustworthy id AND uuid directly or in `.data`; caption/time alone is never ownership proof.

Read-only brand/list response shapes and official input schemas have actual connector evidence from the parent. The parent also recovered verbatim receipts from four previously authorized creates: MCP text JSON contains a single `data` object with numeric safe id, exact string uuid and plannerUrl; later readback is `data:[...]` and omits plannerUrl. This confirms the adapter’s create identity-envelope contract without creating any new post. Fresh readback large negative UUIDs were verified to be strings, so they retain precision. Ingest/readback timing for a new persona MP4 and byte-identical `static.metricool.com` rehosting remain **unverified for these new masters**. Provider transcoding or asynchronous media ingestion can prevent proof even if a post was created; that becomes permanent unknown, not a retry. Exact source bytes remain the approval boundary; no transcoding exception is silently granted. Prior reminders are contract evidence only and are never copied or recreated.

Read-only tool-schema/brand/scheduled-post metadata through an already authorized connector could close name/schema/mapping/readback-shape gaps without any scheduling, upload, credential retrieval or refresh. It would not alone prove byte preservation for a new upload. Introspection through this website's bearer session retrieves/decrypts the saved credential and is outside this implementation task's no-credentials boundary. A separate authorized verification plan is required before activation. Do not schedule a test post or duplicate unrelated previously approved HitEm reminders to gather evidence.

Provider identity precision remains a hard gate even though the recovered real receipts use strings: only exact nonempty strings or safe integers are accepted for id/UUID. A provider UUID represented as a JSON number beyond JavaScript’s safe integer range is rejected, never rounded into ownership proof. If the live server MCP emits such numbers rather than strings, lossless identity transport must be verified before activation.

Provider scheduling serializes whole seconds. The dispatcher SQL preflight, server orchestration and provider adapter therefore reject fractional-second schedules before a claim/transmission; the UI requires explicit reauthoring/reapproval and uses whole-second inputs. Existing .123Z or microsecond values are displayed unchanged, never rounded. Database revision and content-approval timestamps continue to retain their full PostgreSQL precision; this provider schedule restriction does not alter them.

The provider's local dateTime also omits UTC offset. For the verified America/Chicago mapping, the dispatcher blocks repeated fall-back wall times instead of choosing a DST fold. The server, UI and private SQL advisory/claim checks compare nearby UTC instants at ±30/60/90/120 minutes; either UTC instant that renders the same local timestamp is rejected. For example, both 2027-11-07 06:30Z and 07:30Z are unsupported, while 08:30Z is unambiguous. The user must explicitly choose and approve a different slot. First-claim cohort readiness applies the same precision/ambiguity requirement to all active siblings, so it cannot freeze a sibling into an undispatchable slot. This bounded check is not a general historical calendar engine or permission to broaden the verified account/timezone mapping.

Production metadata parity correction: the existing delivery schedule is nullable while status is blocked_assets, enforced by the existing `cs_character_promo_delivery_schedule_guard` CHECK. Candidate and control evidence preserve an unscheduled value as null, so missing-time plans remain available for authoring or explicit withdrawal. They never become dispatch-ready through that display. The disposable production-shaped regression overlays this known constraint on the older fixture; no production guard or stored value is removed or changed by any proposal.
