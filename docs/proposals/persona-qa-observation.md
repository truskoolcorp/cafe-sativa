# Exact-hash QA observation (offline only)

Apply ordering, if separately authorized: existing ledger, gates, owner revocation, then `persona-qa-observation.sql`. This file is not a production migration. No activation or provider operations are included.

RPC `cs_record_character_promo_qa_observation` accepts `p_promo_id` UUID, `p_video_sha256` lowercase SHA256, `p_draft_revision` timestamptz (the viewed draft's updated_at), `p_check_name`, explicit `p_result` (pass/fail/needs_review), nonblank `p_evidence` (up to 1000 characters), `p_expected_observation` JSON object or SQL null, and server-only `p_actor` UUID. Present expected observation must contain exactly all eight typed table fields; null means explicitly observed absence. RPC returns the full saved observation row or SQL null for stale/invalid conflict. Exceptions must be sanitized by the API, never forwarded verbatim.

The server must freshly call auth.getUser and verify `app_metadata.cafe_sativa_admin === true`, supply that user's ID, and never accept an actor from request JSON. SQL independently verifies strict auth.users application metadata before and after locking the parent draft. QA admins need not be final-consent owners. Only the exact reviewed hash, current draft revision, and entire prior observation can be saved. Source/claim serialization uses the existing parent lock. Existing source triggers invalidate prior consent, without editing approval stamps or issuing final approval. Explicit results are user supplied; the function never infers PASS from uploaded bytes or other checks.

Local verification: `run-persona-qa-single.py` performs actual isolated PG17 installation/assertions without sockets. Synthetic fixture observations are not human reviews. Hosted `run-persona-qa-ci.sh` adds actual separate-session contenders, media replacement and waited-admin-revocation races; it has **not been run locally**. It requires a fresh isolated CI PostgreSQL instance whose fixture roles do not yet exist. Serial CAS assertions are not race certification.

## Runtime integration and existing writer audit

`record_qa` requires promoId, videoSha256, draftRevision, checkName, result, evidence, expectedObservation and explicitConfirmation=true. The server rereads and hashes actual media bytes, then freshly verifies admin/reviewer identity before invoking SQL. It checks the returned full row against target, check, explicit result/evidence and reviewer; conflicts or uncertain receipts return sanitized unconfirmed responses with no retry.

When the runtime flag is enabled, the older qa-checks POST delegates to the strict runtime action contract, rejecting legacy submissions that lack displayed media identity, revision and prior CAS. When disabled, the pre-existing route behavior is unchanged. This does not repair the disabled legacy production path.

Writer audit of app/lib/scripts found two other existing writers: `media-upload/route.ts` and `upload-finalize/route.ts` under admin/programming/character-promos. Both write automatic mp4_integrity PASS without reviewer_id. They were not changed by this scoped task. Such rows are machine evidence, not proof of a human review. An existing observation with null reviewer is permitted as the exact prior CAS so a verified admin can explicitly replace it; a new receipt must have the fresh reviewer identity. Other current QA reads include candidate material, source loading, readiness, schedule preview, production packets and admin character promotions. Broader downstream human-review provenance enforcement is a separate integration requirement; do not interpret historical PASS rows as proof of explicit human viewing.
