# Durable concierge candidate: deployment gates and contract

Local implementation candidate only. No migration, grants, external database changes, provider calls, or rollout are implied by these files. Applying this candidate requires separately reviewed approval of the exact target and SQL.

## RPC boundary

Five SECURITY INVOKER RPCs use an empty search path and server-role-only execution. Arguments follow the signatures in the migration. Authentication, membership resolution, stable client IDs and identity pinning remain server responsibilities. A new `p_payload` has exactly seven keys: `version:2`, `issued_at` (integer Unix epoch milliseconds), `host`, trimmed `message`, original `conversation_id` (null remains null on retries), `surface`, `room_id`. The UUIDv7 request ID's first 48 bits must exactly equal `issued_at`. Generation uses secure random suffix bits and the browser clock; the database checks issuance against its own clock, the explicitly configured future-skew tolerance, the replay-age limit and the persistent rejection floor. A client cannot make a pruned UUID fresh by editing its body timestamp. Changing the UUID creates a different request, never a retry. Keep the original ID, issuance, payload, conversation and requester namespace unchanged across recovery. Guest session identifiers are bearer identifiers, not proof of personhood.

Six-key version-1 payloads are accepted only to look up an existing retained key. A missing version-1 key returns `request_expired`, even if the browser tries the old admission endpoint. Never silently regenerate an ID or restamp issuance for a pending older request. Future-clock errors require correcting the clock and starting an explicitly new turn, not automatic replay.

RPC results use lowercase state strings. Admission/status/complete return `state`, `request_id`, `conversation_id`, `remaining`, `admitted:false`. A fresh reservation alone sets `admitted:true`, `requester`, `owner_token`, and `policy` with version and prompt/message/output/reply bounds. Completed results contain `response:{message,conversation_id,host,remaining,memory_saved:true}`. No repeat/status lookup reveals an owner token. Errors are `{error:code}` with narrowly defined optional safety markers. Missing eligible version-2 status alone returns `{error:'request_missing',recovery_required:true}` after database-clock validation. Missing version-1 keys and version-2 keys at/below the committed rejection floor return `{error:'request_expired',terminal:true}` because unresolved keys are never pruned and this key cannot be newly admitted. Age-only expiry above that floor returns `request_expired` without a terminal marker: later policy widening or a backwards database clock could otherwise invalidate a promise that the key can never be admitted. Status remains read-only and does not advance the floor. `gone` includes `terminal:true` only when the retained state is completed/cancelled/failed. Redacted or content-expired reserved/dispatching/uncertain rows never receive that marker; clients retain their pending identity. The marker permits clearing a finished pending turn, not automatically resending its text under a new ID. Completion's cancelled lease expiry also returns `terminal:true`. Only the fresh-key explicit-conversation ownership/open rejection returns `{error:'conversation_unavailable',admitted:false}`, proving no ledger row was created. Existing-key owner failures remain `{error:'forbidden'}` without that marker; clients must retain the original request identity. Dispatch grants are boolean and are true only on the first RESERVED→DISPATCHING transition. Finish accepts `no_dispatch`, `uncertain`, or `provider_terminal_failure`; the latter requires actual provider-terminal evidence, never merely elapsed time or local cancellation. Finish intentionally returns no cached reply and never downgrades an already COMPLETED row; it returns its state only. When provider success is known but persistence fails, recheck status after bounded same-completion retries, then close as a charged terminal failure using the original owner token. A concurrent completed commit wins, and its cache must be recovered through status rather than treating a state-only finish result as a reply.

Completion and finish accept an optional final `p_provider_receipt jsonb DEFAULT NULL` argument. If supplied it has exactly `request_id`, `message_id`, `input_tokens`, `output_tokens`, each nullable. IDs are 1–128 ASCII letters/digits/underscore/hyphen; counts are nonnegative integers at most 2,147,483,647. Populate only from the provider SDK's sanitized IDs/usage. No prompt, reply, credential, raw exception, URL or arbitrary metadata is permitted. Absence is safe; a receipt alone is not proof that a request is terminal. Receipts are never returned by public RPCs and are erased with ledger content on retention or deletion. A late receipt cannot repopulate a redacted request.

Same-ID admission recovers an expired undispatched reservation into cancelled/refunded, never a new token. Unknown dispatched work stays charged and holds capacity indefinitely until evidence-based reconciliation. Provider response persistence is atomic with both messages; retries after persistence failure must repeat completion, never the provider call. No automatic provider retry exists.

## Authoritative policy and spend

The singleton policy starts disabled with every material admission/budget/window/lease/retention setting NULL. Lifecycle decisions are explicit: `content_retention_seconds`, `replay_max_age_seconds`, `retention_seconds` (minimum terminal-tombstone duration), and `max_future_skew_seconds`. The 0–300-second skew range and 100-year upper duration bound are technical validity limits, not chosen settings or approved retention policy. Terminal retention is at least 24 hours to cover every current rolling accounting window. New rows snapshot content expiry and terminal-retention duration so a later policy change cannot silently extend a promised content cache or shorten already admitted terminal retention. The service role can read but cannot modify it. New admissions fail closed until explicit operator configuration, legacy drain, failure charging approval and retention configuration are present. Same-ID recovery, status, completion and finish stay available when admissions are disabled.

Tier allowances remain anonymous 10/hour, explorer 50/day, regular 200/day, VIP 1000/day. Requester inflight is one. Global inflight, rolling admission limit and rolling conservative reserved-cost budget are independent limits. The operator must derive `max_request_cost_microusd` from the actual model pricing and enforced maximum aggregate prompt/output, then review `global_budget_microusd`; these are **not** measured provider bills. All charges reserve that upper bound, including terminal failures and local replies. Hard technical ceilings are 48,000 prompt UTF-8 bytes, 61 messages, 512 output tokens and 16,384 reply characters. Missing/bad policy must never fall back to legacy count-before-call logic.

## Locking, deletion and all writer inventory

All guarded mutations, including direct ledger writes and cleanup, begin with global advisory transaction lock `(1128351301,1)` and use READ COMMITTED. RPCs then lock request and conversation. Statement triggers acquire global lock before existing-table row updates/deletes and profile cascades; message inserts lock the conversation and enforce monotonic timestamps. Profile identity-only UPDATE OF id, DELETE and TRUNCATE are also guarded before their tuple locks to avoid the admission-versus-profile-delete FK inversion. All newly created functions are INVOKER; client roles lacking private-schema access fail closed on the private guarded mutations. A separate public lock-only INVOKER trigger coordinates Auth hard deletion and Lounge updates without any private-schema access. Three existing service-only commerce RPCs retain their existing SECURITY DEFINER status, owner and ACLs, with only an early lock call inserted. Existing service permissions on existing tables are not broadened or revoked.

**Triggers affect behavior immediately even when policy.enabled=false.** This is not a behavior-neutral additive deployment. Applying triggers requires the full writer/cascade/deletion review first; do not stage this whole migration under the assumption that disabled admission disables guards. They deny TRUNCATE, forbid owner/host/end changes during unresolved requests, forbid message identity/role/time changes, and block non-ledger message inserts while text work is unresolved. Direct client conversation/message writers and profile deletion/identity updates may now fail. Unrelated authenticated profile edits do not invoke the private lock; the role fixture verifies an ordinary display-name edit remains usable. Operators must approve and test that boundary before any hosted application.

Source inventory (repository snapshot 2026-11-08; deployment drift remains a separate verification gate):

- `app/api/concierge/route.ts`: legacy conversation create and paired message insert are replaced by admission/completion RPCs in this change.
- `app/api/concierge/livekit/memory/route.ts` POST: direct stable-event voice message insert. Statement and row guards serialize insert and protect unresolved text context. Voice request quotas/provider calls are outside this text ledger; a site-wide spend claim would be false.
- `app/api/concierge/livekit/session/route.ts`: reads conversation owner/host/end only.
- `lib/concierge/memory.ts`, `rate-limit.ts`: read-only message/history usage; legacy rate limiting must not remain the durable route's fallback.
- `public.bump_message_count`: message insert trigger updates conversation count; guarded statement locks are reentrant, and nonidentity/count-only changes remain allowed.
- `public.profiles` deletion: FK cascade can delete conversations and messages. A profile statement trigger takes the global lock first; conversation deletion creates detached redacted tombstones before the FK check/cascade.
- `auth.users` hard deletion and identity change: `concierge_auth_delete_statement` (BEFORE DELETE) and `concierge_auth_identity_statement` (BEFORE UPDATE OF id) call `public.concierge_auth_statement_v1()` before auth tuple/FK locks, inside the actual Auth service transaction. The lock-only helper uses only a built-in advisory lock, has an empty search path and a two-second lock timeout, and receives no client/service/auth-admin EXECUTE grant. PostgreSQL invokes the installed trigger without requiring that grant. No auth-admin private-schema access is granted. Auth signup, sign-in/refresh and ordinary/soft-delete UPDATEs are not guarded. Soft deletion does not delete profile/history or constitute concierge privacy erasure.
- `public.cs_record_gallery_payment(jsonb,uuid,uuid,integer)`, `public.cs_reserve_ticket(uuid,uuid)` and `public.cs_record_ticket_payment(uuid,jsonb)`: take `concierge_private.lock_v1()` before their first row/FK lock. An auth guard alone cannot protect a product-first payment writer. Source, owner, language, ACL and configuration assertions reject missing/drifted live definitions. The rest of each catalog-verified body is preserved. Checkout/reservation/payment persistence now shares the global contention and two-second acquisition timeout, even when text admissions are disabled.
- `public.lounge_messages` UPDATE: a public lock-only BEFORE STATEMENT guard precedes the tuple lock and the existing soft-delete trigger's `deleted_by` auth FK check. Existing author/moderator authorization, RLS, ACLs and soft-delete function remain unchanged. INSERT and DELETE are not newly guarded.
- Direct single-statement orders/memberships inserts do not enter the concierge lock and need no blanket new table guards. Existing content claim functions do not mutate an auth FK or enter concierge after their job/asset locks. They are not changed.
- No application source owner transfer, host change, end-conversation update, conversation/message delete, profile/account-delete endpoint or scheduled retention writer was found in this snapshot. External admin SQL, Supabase dashboard actions, auth-user cascades, storage jobs and deployed DB functions/triggers must still be inventoried in the target DB. Repo absence is not proof no other writer exists.

Conversation deletion removes payload, fingerprint, cached response, provider receipt and conversation FK from all linked ledger rows. It does not refund or free dispatched/uncertain capacity. Tombstones retain requester/key, host, capability, accounting and lifecycle metadata; the request cannot be replayed. Message deletion/content editing redacts the associated cached ledger content. Updates cannot move or reorder a message. Reserved tombstones may still be safely cancelled by a worker or ordinary expiry; dispatched tombstones require terminal evidence. User/profile identifiers in tombstones are still personal data: a retention/privacy decision is mandatory.

## Local lifecycle candidate, not an activated retention job

`concierge_private.maintain_v1(p_limit)` is an owner-only SECURITY INVOKER cleanup candidate. The migration gives no service-role execute permission for it, no DELETE/TRUNCATE on the ledger, and no ability to write the rejection floor or policy. It creates no cron entry, scheduler, new role, credential or SECURITY DEFINER privilege path. Do not invoke it on real data without the required review and action-time authorization. The fixture invokes it only against disposable synthetic rows and rolls everything back.

Each call requires an explicit integer batch size 1–1000 and complete lifecycle configuration, takes the same global transaction lock as admission/status/deletion, and selects at most that many rows with `FOR UPDATE SKIP LOCKED`. Every row counted in the batch may have several changes, but the call never processes additional rows as an unbounded catch-up. Configure an outer session timeout as well; function-level timeouts do not prove a whole-RPC deadline. The work is:

1. Advance the non-personal singleton `lifecycle.reject_before_ms` to the largest previously established floor or current database time minus replay age. The floor never decreases, even if replay age is later enlarged. Update and pruning commit atomically under the same lock. Never delete, reset or restore an older floor independently of the ledger.
2. Cancel/refund only RESERVED rows whose undispatched lease has expired. Dispatched/uncertain work never expires into a refund.
3. Remove payload, fingerprint, reply cache and provider receipt when the per-request content deadline is reached. Admission/status/complete also refuse to serve expired content even if the job is late. This does not remove existing public member conversation history, whose policy remains separate.
4. Mark redacted unresolved rows with `quarantined_at`; dispatched rows become UNCERTAIN. Keep their charge, capacity, owner capability and key for evidence-based reconciliation. A timeout, lack of a response, old age or privacy deletion is not evidence of provider termination. These exceptions do not have a finite automatic deletion promise and must generate operator attention.
5. Compact terminal redacted rows by removing duplicate user/session identity, host/conversation/message IDs, owner capability, tier, policy label and response-display fields. The remaining requester/key and lifecycle/accounting metadata are still personal data, not anonymous data.
6. Prune only redacted COMPLETED/CANCELLED/FAILED rows with a non-null completion timestamp, outside both their captured and current terminal-retention durations, outside the full 24-hour accounting window, and whose UUIDv7 issuance is at/before the durable rejection floor. Legacy non-v7 IDs cannot ever be fresh version-2 requests and may be pruned only under the same terminal/accounting/retention conditions. Unresolved rows are never pruned. Unknown/missing terminal evidence fails closed.

The request key/issuance are immutable through a ledger trigger. The floor has monotonic-update and delete/truncate guards. These are application safety barriers, not a claim that a database owner cannot bypass its own triggers or that arbitrary trusted service-role SQL satisfies all RPC invariants. Direct ledger writers and restore procedures remain part of the reviewed boundary.

Before activation, separately approve actual retention values and cleanup cadence, a least-privileged operational execution path, exception owner/alerts, and the exact real-data action. Verify the job and alarms in an isolated environment first. No automated finite retention is currently running or promised. Successful privacy deletion clears ledger content immediately through existing deletion guards; terminal pruning does not authorize unrelated history deletion.

## Cutover, validation and operational constraints

Drain and disable old route workers before configuring `legacy_cutoff`/`legacy_drained`. Admission counts legacy user messages strictly before cutoff plus durable charges. The bridge does not authorize concurrent legacy writers; those would evade durable global cost/count controls. Do not reset quota or silently switch back to count-before-call on failure. Disable new admission first on rollback, retaining status/completion/finish and tombstones.

The coarse lock deliberately trades throughput for safety and may exhaust capacity indefinitely on uncertain dispatch. Name a reconciliation operator and define provider-terminal evidence before enabling. SQL function-level statement_timeout settings alone do not establish a wall-clock bound for the outer PostgREST SELECT. Configure and test the session/PostgREST statement timeout and lock timeout explicitly; connection-level timeout is used by the integration harness. An aggregate budget cap here is a policy estimate, not provider financial reconciliation.

Required gates: exact production schema/grants/trigger inventory; full independent-connection races and lock/deadlock tests; auth/profile cascade and deletion behavior under actual roles; read-only/cached privacy checks; drain/cutover evidence; bounded prompt/cost policy; operator reconciliation and retention plan; independent code review; separately approved target migration and controlled acceptance test. The expanded synthetic fixture reproduces the catalogued auth/profile graph, role ownership and blocking references, but abbreviated row shapes are not a proof of the full live schema. The source candidate now puts the hard-delete boundary inside the actual `auth.users` DELETE statement and the identified commerce/Lounge writer boundaries, not in a separate preflight transaction or a replacement account-deletion RPC. Continue to use the Auth service so its audit, session, storage-owner and other lifecycle checks remain in force. The live read-only health endpoint reports GoTrue v2.197.0, and the matching upstream tag supports this transaction placement; service-level deletion with the full hosted schema/storage integration has not been exercised. Arbitrary administrator transactions that lock rows before calling these entry points remain outside the protocol; they must acquire the same global lock before their first participating row/FK lock. Review `docs/concierge-cutover-runbook.md` and repeat isolated concurrent verification of the exact candidate before any deployment decision. The local candidate is not launch-ready merely because sequential tests pass.
